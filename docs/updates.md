# Auto-update for Pylair apps

> **Not available yet.** This doc ships ahead of the feature: the commands
> below land across the auto-update series (decision
> [0011](decisions/0011-auto-update.md)). Until the client API and the
> readiness-gated rollback arrive, an updater-enabled app can check for
> and install updates through `tauri-plugin-updater`'s own API — it just
> won't get Pylair's rollback, `pylair.update` client surface, or update
> state in `health()` yet.

Pylair apps ship as installers; without update machinery every release is
a manual reinstall. Auto-update adds three things on top of
`tauri-plugin-updater`: full-bundle signed updates, a readiness-gated
rollback watchdog (a broken release restores the previous version instead
of stranding the install), and a skip list so a failed version is never
re-offered.

## Setup

### 1. Scaffold with the updater

```sh
npx create-pylair my-app --with-updater   # or answer "yes" at the prompt
```

This adds `tauri-plugin-updater` to `src-tauri/Cargo.toml`, a
`plugins.updater` block and `bundle.createUpdaterArtifacts` to
`tauri.conf.json`, the `updater:default` permission to the default
capability, and `*.key` to `.gitignore`. The scaffold's
`nsis.installMode` stays `currentUser`: per-user installs update and roll
back silently, per-machine installs would need UAC elevation (0011 §2).

The conf lands with placeholders:

```json
"plugins": {
  "updater": {
    "pubkey": "<generated by pylair keys init>",
    "endpoints": ["https://example.com/releases/latest/download/latest.json"],
    "windows": { "installMode": "quiet" }
  }
}
```

### 2. Generate signing keys

```sh
npx pylair keys init --key-path ~/keys/myapp-updater.key
```

`keys init` wraps `tauri signer generate` (minisign). It refuses paths
inside the repository containing the app unless git-ignored (verified via
`git check-ignore`) — in a monorepo that boundary is the repo root, so a
key at the root or in a sibling package is refused the same way. The
pubkey goes into `plugins.updater.pubkey`, and the storage rules print.
Re-running against an existing pubkey is refused: rotation means
shipping an update signed by the *old* key that embeds the new pubkey —
`--force` only when you know what you're doing (0011 §6).

Password handling, in order: `--password`, the
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` env var, the tauri CLI's own prompt
on a TTY, or `--no-password` for a deliberately unprotected key (warned;
never implied — a failed generation is never silently retried with a
weaker password). Two caveats: `tauri signer generate` only accepts the
password via `-p` on its command line (no env/stdin support), so it can
appear briefly in process listings — prefer the interactive prompt where
that matters. And a non-interactive shell with none of the three sources
fails rather than guessing.

Store the private key safely:

- **CI**: `TAURI_SIGNING_PRIVATE_KEY` (file contents) and
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` as secrets.
- **Offline backup** — losing the key means installed copies can never
  update again; recovery is a manual reinstall campaign.
- Rotation ships a new pubkey inside an update signed by the old key;
  there is no in-band revocation.

### 3. Build signed artifacts

```sh
TAURI_SIGNING_PRIVATE_KEY=… npx pylair build --sign
```

`--sign` requires `TAURI_SIGNING_PRIVATE_KEY` in the environment and
forces `bundle.createUpdaterArtifacts`, producing the signed payloads
next to the installers: `*-setup.exe` + `.sig` (Windows), `*.app.tar.gz`
+ `.sig` (macOS), `*.AppImage` + `.sig` (Linux).

Two build-time guards fire for updater-enabled apps:

- `tauri.conf.json` `version` must equal `src-tauri/Cargo.toml`
  `[package] version` — the updater compares offers against the conf
  value while the running binary reports the Cargo one; a drifted pair
  misreports the app's version after an update (0011 §1).
- macOS App Translocation: an app launched from a DMG or quarantined
  location can't update in place; the update path refuses with a clear
  message to move the app first.

### 4. Publish the manifest + artifacts

```sh
npx pylair update manifest \
  --base-url https://github.com/ORG/REPO/releases/latest/download \
  --notes "what's new"
```

`update manifest` scans `src-tauri/target/.../release/bundle` for the
signed artifacts, checks every `.sig` exists and every artifact's version
agrees with `tauri.conf.json` — from the filename where it carries one,
and on macOS from the `CFBundleShortVersionString` inside the
`.app.tar.gz`'s `Contents/Info.plist` (the name carries none, so a stale
bundle can't slip in under the new version) — and writes `latest.json`:

```json
{
  "version": "0.2.0",
  "pub_date": "…",
  "platforms": {
    "windows-x86_64": { "signature": "…", "url": "…/app_0.2.0_x64-setup.exe", "sha256": "…" },
    "darwin-aarch64": { "signature": "…", "url": "…/app.app.tar.gz", "sha256": "…" },
    "linux-x86_64":   { "signature": "…", "url": "…/app_0.2.0_amd64.AppImage", "sha256": "…" }
  }
}
```

The `sha256` is a Pylair extension the update plugin ignores and the
rollback machinery uses as artifact identity (0011 §3). Upload
`latest.json` plus each artifact and `.sig` as release assets — a static
`…/releases/latest/download/latest.json` on GitHub Releases is all the
hosting needs to be (0011 §6). The `--base-url` defaults to your
endpoint minus its filename, so it usually stays unset.

### Channels

`--channel beta` writes `latest-beta.json` instead of `latest.json`:
channels are separate manifest files on the same release, and an app
pins one by its endpoint URL. Cheap, reviewable, no server.

A `universal-apple-darwin` build is listed under **both**
`darwin-aarch64` and `darwin-x86_64` — one fat artifact serves both
arches, so `update manifest` registers it twice (detected from the
`--target` triple dir or a `_universal` arch token in the filename).

## App-side API

Everything below runs on apps scaffolded `--with-updater` (the crate's
`updater` cargo feature + a `plugins.updater` block); calls on any
other app reject with `UpdateError` code `NotUpdatable`.

### Client (`@pylair/client`)

```ts
import { update, onHealth } from "@pylair/client";

const offer = await update.check();          // {version, notes, sha256, current} | null
await update.downloadAndInstall({
  onEvent: (e) => {                          // upstream's event shapes
    // Started {contentLength} | Progress {chunkLength} | Finished
  },
});
await update.relaunch();                     // restart into the new version
```

- `check()` returns `null` when nothing is offered — including when the
  artifact is on the skip list, so a rolled-back build is never
  re-presented.
- On **Windows** the install never returns: the process exits into the
  installer. Everything the watchdog needs (cached rollback artifact,
  `pending.json`) is armed before that call.
- Errors throw `UpdateError` with a stable `updateCode`:
  `NotUpdatable` (no updater config, macOS App Translocation — move the
  app to `/Applications`), `NeedsApproval` (per-machine Windows
  install), `SignatureInvalid`, `NoOffer`, `EndpointError`,
  `CheckFailed`, `DownloadFailed`, `CacheFailed`, `InstallFailed`.
- `health().update = {state, lastRollback?}` tracks the lifecycle:
  `pending` | `installing` | `ready` | `rolled-back` |
  `rollback-pending-approval` | `none`. The same vocabulary appears as
  the `updating` readiness component under `health().app.components`.
- Verification knobs live under `plugins.pylair.update` in
  `tauri.conf.json` and are copied into `pending.json` for the
  watchdog: `heartbeatMs` (default 60 s of silence ⇒ dead), `maxBoots`
  (default 3 failed boots ⇒ crash loop), `hardCapMs` (default 10 min —
  the only wall clock; live component progress keeps the window open).

### Python (`pylair.update`)

```python
from pylair import update

if update.state() == "pending":          # "none" | "pending" | "confirmed"
    run_read_only_mode()                  # a rollback is still possible
update.on_update_confirmed(migrate_state) # runs once the update is proven
```

`"pending"` means this boot is the update's verification window — run
read-only, defer schema/state migrations until `on_update_confirmed`
fires (the watchdog wrote `update-ok`). If the update rolls back the
hook never runs: a restored build has nothing to migrate. Migrations
must tolerate the previous version reading the files they write
(decision 0011 §4).

## Security notes

- **Signatures are mandatory.** The updater verifies every artifact
  against the compiled-in pubkey; there is no bypass flag, and the
  rollback path re-verifies the cached artifact (minisign vs a pubkey
  compiled into the watchdog) before reinstalling — a tampered cache
  never executes.
- **https only outside dev.** Endpoints are rejected at plugin init on
  plain http unless `dangerousInsecureTransportProtocol` is set, which
  exists for local dev/CI servers only (`--insecure-dev` on
  `update manifest` is the matching CLI escape hatch).
- **A compromised endpoint can withhold, never forge.** Worst case is no
  update, or a valid update not offered — an attacker cannot push an
  unsigned or forged bundle. The private key is the single point of
  compromise; treat it as long-lived and precious (0011 §6).

The remaining pieces from 0011 arrive in the rest of the series: the
